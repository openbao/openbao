# Per-Namespace Auto Seals

## Summary

Per-namespace sealing, introduced in OpenBao v2.6, allows individual namespaces
to maintain their own barrier protected by a dedicated seal. This RFC extends
that feature to support Auto Seal backends (HSMs and KMSes) at namespace
creation, defines a dedicated endpoint for credential and key updates, specifies
the seal type migration path, and establishes the authorization and cluster
coordination model required to operate namespace seals safely.

## Problem Statement

The namespace creation endpoint rejects non-Shamir seal types
(`logical_system_namespaces.go`, `handleNamespacesSet`). No endpoint exists for
updating seal credentials or migrating seal types on an existing sealable
namespace (`logical_system_namespaces_seals.go`, `namespaceSealPaths`). The
`sys/namespaces` path is not listed in `PathsSpecial.Root` (`logical_system.go`),
so any token with `update` capability can modify namespace properties including
seal configuration. The invalidation framework (`invalidation.go`,
`isCoreKeyPath`) does not cover namespace seal configuration changes, leaving
standby nodes with stale wrappers after a credential update.

## User-Facing Description

### Creating a Sealable Namespace with an Auto Seal

The `seal` parameter on `POST /v1/sys/namespaces/<path>` already accepts an HCL
or JSON seal configuration string. This RFC removes the Shamir-only restriction,
allowing any seal type supported at the global level. See the
[API documentation](/docs/api/system/namespaces) for the exact request format.

When an Auto Seal type is specified, no recovery key shares are generated or
returned at creation time. The namespace is born unsealed: the barrier key is
wrapped by the KMS immediately and the namespace is operational without any
manual unseal step. This mirrors the behavior of the global Auto Seal, where key
shares are absent and the KMS is the sole unseal authority.

If the KMS is later decommissioned, the operator uses `POST /migrate-seal` to
migrate the namespace to Shamir, at which point key shares are generated and
distributed. Recovery key shares are not a substitute for a planned migration;
operators are encouraged to perform the migration before decommissioning the KMS
key rather than relying on emergency recovery paths.

### Updating Seal Credentials and Keys

| Method | Path                                    |
| ------ | --------------------------------------- |
| `PUT`  | `/v1/sys/namespaces/<path>/config/seal` |

This endpoint requires sudo privilege. It accepts the same seal configuration
string format as namespace creation. It handles credential rotation only: the
seal type and KMS key must remain the same; only the credentials used to reach
the KMS may change. The new wrapper must successfully decrypt the existing stored
barrier key (`GetStoredKeys`) before the old wrapper is released. If verification
fails, the update is rejected and the existing configuration is kept intact.

The namespace remains accessible throughout. The operation is synchronous.

Key migration (changing to a different KMS key or a different provider) requires
`POST /migrate-seal`.

### Reading Seal Configuration

| Method | Path                                    |
| ------ | --------------------------------------- |
| `GET`  | `/v1/sys/namespaces/<path>/config/seal` |

Returns the `Metadata` map from the `WrapperConfig` produced by
`Wrapper.SetConfig()`, which provides provider-supplied configuration metadata.
Sensitive fields (credentials, tokens, passwords) are omitted by the plugin;
non-sensitive fields (provider type, endpoint, key identifier) are returned.
This is the same mechanism used to produce the seal information table printed
at server startup.

This endpoint is distinct from `seal-status`, which reports runtime
sealed/unsealed state. The response intentionally omits credentials and key
material; the full seal configuration is never returned.

### Seal Type Migration

| Method | Path                                     |
| ------ | ---------------------------------------- |
| `POST` | `/v1/sys/namespaces/<path>/migrate-seal` |

This endpoint requires sudo privilege. It handles seal type changes between
Auto Seal and Shamir within a sealable namespace. The operator provides the
new seal configuration in the request body.

- **Auto Seal to Shamir**: new key shares are returned in the response.
- **Shamir to Auto Seal**: existing key shares must be provided in the request;
  after reconstruction the combined key becomes the recovery key on the new
  Auto Seal via `SetRecoveryKey`.

The root key is re-encrypted under the new seal. No storage copying is required.
The namespace remains accessible throughout. The operation is synchronous.

Normal-to-sealable and sealable-to-normal conversions are out of scope and
tracked in https://github.com/openbao/openbao/issues/3333.

### Failure Conditions

#### KMS unreachable at server startup

If the KMS provider is unreachable during server startup, OpenBao records the affected namespace in an internal tracking list and allows the server startup sequence to complete normally. The root namespace and all other namespaces remain unaffected.

The namespace associated with the unavailable KMS is registered as sealed. Its barrier remains present in storage but cannot be decrypted because the required key material cannot be retrieved from the KMS. Consequently, the namespace initialization sequence cannot proceed, and its mounts and auth backends are not loaded.

A background goroutine (`startSealedAtBootRetry`) periodically retries access to the KMS using the same interval configured for the root seal health check, which defaults to one minute.

Once the KMS becomes reachable, the goroutine invokes `GetStoredKeys` to retrieve and decrypt the stored barrier key, followed by `UnsealWithRootKey` to open the namespace barrier. OpenBao then executes the standard post-unseal initialization sequence, including loading the namespace mounts and policies.

Recovery is fully automatic and requires no operator intervention.

During the retry period, `GET /v1/sys/namespaces/<path>/seal-status` reports the namespace as sealed. After the KMS becomes available and the recovery sequence completes successfully, the endpoint transitions to reporting the namespace as unsealed.

#### KMS unreachable after boot

If the KMS becomes unreachable after the namespace has already been successfully unsealed, normal namespace operation is unaffected.

At that point, the barrier keyring is already resident in memory, and OpenBao does not require access to the KMS for routine barrier encryption or decryption. Normal read and write operations therefore continue without interruption for the duration of the KMS outage.

The KMS outage becomes relevant only when OpenBao performs an operation that requires the barrier key to be re-wrapped, such as a credential rotation. Such operations cannot complete while the KMS remains unavailable.

No automatic recovery mechanism is required for this condition because the namespace itself remains unsealed and operational. Once KMS connectivity is restored, operations requiring access to the KMS can proceed normally.

The [Emergency Seal](emergency-seal.mdx) and [Parallel Unseal](parallel-unseal.mdx)
RFCs address persistent KMS failure where the barrier key cannot be recovered.

## Technical Description

### Credential and Key Updates (PUT /config/seal)

`SealManager.SetSeal` in `seal_manager.go` already initializes seal wrappers
and stores them by namespace UUID. This RFC extends it to handle credential
rotation on existing seals, adding the test-before-swap guard described below.

Sealing a parent namespace implicitly makes all descendant namespaces
inaccessible, regardless of their individual seal configuration. This is
existing behavior introduced in v2.6 and is not modified by this RFC; no
background job is added for cascade seal or unseal.

`SetSeal` handles credential rotation only: same seal type, same KMS key,
updated credentials. If the seal type changes, the request is rejected outright.
If the seal type is unchanged but an auto-seal type is involved, `GetStoredKeys`
is called on the new wrapper to verify it can still decrypt the existing stored
barrier key before the old wrapper is released. If that verification fails, the
update is rejected and the existing configuration is kept intact. This is the
test-before-swap guard implemented in the proposed solution.

Key migration (changing to a different KMS key or a different KMS provider)
is not handled by this endpoint; it requires `POST /migrate-seal`.

```go
if existingSeal.BarrierType() != nsSeal.BarrierType() {
    _ = nsSeal.Finalize(ctx)
    return fmt.Errorf("cannot change seal type for namespace %q: "+
        "migration from %q to %q is not supported via this endpoint",
        ns.Path, existingSeal.BarrierType(), nsSeal.BarrierType())
}

// For auto-seal reconfiguration, verify the new wrapper can decrypt the
// existing stored barrier key before committing.
if prevSeal != nil && nsSeal.BarrierType() != vaultseal.WrapperTypeShamir {
    if _, err := nsSeal.GetStoredKeys(ctx); err != nil {
        _ = nsSeal.Finalize(ctx)
        return fmt.Errorf("new seal cannot read existing stored keys for namespace %q: "+
            "the KMS key must remain unchanged; only credential rotation is supported: %w",
            ns.Path, err)
    }
}

_ = prevSeal.Finalize(ctx)
sm.sealByNamespace[ns.UUID] = nsSeal
```

### Configuration Metadata (GET /config/seal)

`Wrapper.SetConfig()` returns a `wrapping.WrapperConfig`; the GET endpoint
exposes its `Metadata` map, whose entries are chosen by the plugin author to
exclude sensitive material. OpenBao already uses this output to produce the
seal information table printed at server startup (`seal_manager.go`). The GET
endpoint returns the same map, requiring no additional redaction logic in core
and no changes to `go-kms-wrapping`.

### Seal Type Migration (POST /migrate-seal)

Changing the seal type -- including between two different Auto Seal backends --
requires exchanging key shares and therefore warrants a separate endpoint.
`SealManager.MigrateBarrierKey` is the new entry point, registered in
`namespaceSealPaths` in `logical_system_namespaces_seals.go`.

The operation mirrors `migrateSeal` in `core.go`, applied at namespace scope.
Only the stored root key entry (`StoredBarrierKeysPath` equivalent for the
namespace) is rewritten; the barrier keyring and all namespace storage remain
untouched. Three cases are handled:

**Auto Seal to Auto Seal**: the recovery key and stored barrier keys are read
from the old seal and written to the new seal via `GetStoredKeys` /
`SetStoredKeys` / `SetRecoveryKey`. No key shares are exchanged.

**Auto Seal to Shamir**: the recovery key from the old seal becomes the Shamir
KEK. The caller receives the resulting key shares in the response. The stored
barrier keys are re-encrypted under the new Shamir wrapper via `SetStoredKeys`.

**Shamir to Auto Seal**: the caller provides existing key shares in the request;
these authorize the operation and become the recovery key on the new Auto Seal
via `SetRecoveryKey`. A new root key is generated, written via `RotateRootKey`,
and stored under the new seal via `SetStoredKeys`.

The operation is synchronous. The amount of data written is constant: at most
three storage entries regardless of namespace size. A migration flag written
before finalizing the old seal allows crash recovery on restart. Both the old
and the new seal must remain reachable until the migration flag is cleared; the
old seal must not be decommissioned before that point.

```go
func (sm *SealManager) MigrateBarrierKey(
    ctx context.Context,
    ns *namespace.Namespace,
    oldSeal Seal,
    newSeal Seal,
    combinedKey []byte, // nil for Auto-to-Auto and Auto-to-Shamir
) error {
    switch {
    case oldSeal.RecoveryKeySupported() && newSeal.RecoveryKeySupported():
        // Auto to Auto
        recoveryKey, err := oldSeal.RecoveryKey(ctx)
        if err != nil {
            return err
        }
        if err := newSeal.SetRecoveryKey(ctx, recoveryKey); err != nil {
            return err
        }
        barrierKeys, err := oldSeal.GetStoredKeys(ctx)
        if err != nil {
            return err
        }
        return newSeal.SetStoredKeys(ctx, barrierKeys)

    case oldSeal.RecoveryKeySupported():
        // Auto to Shamir
        recoveryKey, err := oldSeal.RecoveryKey(ctx)
        if err != nil {
            return err
        }
        shamirWrapper, err := newSeal.GetShamirWrapper()
        if err != nil {
            return err
        }
        if err := shamirWrapper.SetAesGcmKeyBytes(recoveryKey); err != nil {
            return err
        }
        barrierKeys, err := oldSeal.GetStoredKeys(ctx)
        if err != nil {
            return err
        }
        return newSeal.SetStoredKeys(ctx, barrierKeys)

    case newSeal.RecoveryKeySupported():
        // Shamir to Auto
        if err := newSeal.SetRecoveryKey(ctx, combinedKey); err != nil {
            return err
        }
        newRootKey, err := sm.NamespaceBarrier(ns.Path).GenerateKey()
        if err != nil {
            return err
        }
        if err := sm.NamespaceBarrier(ns.Path).RotateRootKey(ctx, newRootKey); err != nil {
            return err
        }
        return newSeal.SetStoredKeys(ctx, [][]byte{newRootKey})
    }
    return errors.New("unhandled migration case")
}
```

### Authorization

All three routes are registered in `namespaceSealPaths`
(`logical_system_namespaces_seals.go`). `PUT /config/seal` and
`POST /migrate-seal` require `update` capability on the namespace path.
These operations act on the namespace's own root key, not on the global seal
or any parent namespace's seal; no elevated privilege beyond namespace
`update` is required.

### Cluster Behavior

All seal lifecycle operations are initiated on the active node, consistent
with general write behavior. After a credential or key update, standby nodes
hold stale wrappers in memory until invalidated. The existing framework in
`invalidation.go` is extended in `buildInvalidateJobForKey` to detect writes
to namespace seal configuration paths and call `sealManager.ReloadSealConfig`
on each node. The resulting invalidation window is the same as for root-level
seal credential updates; no additional mechanism is required.

```go
case strings.HasPrefix(key, "sys/namespaces/") &&
    strings.HasSuffix(key, "/config/seal"):
    ns := c.extractNamespaceFromKey(key)
    c.sealManager.ReloadSealConfig(ctx, ns)
```

Seal key updates are written to storage and propagated to standby nodes via
the existing invalidation broadcast; no additional mechanism is required.

### Boot-Time KMS Failure Recovery

When a namespace KMS is unreachable at startup, `RegisterSealedBarrier` in
`seal_manager.go` registers a bare sealed barrier so that `NamespaceSealed`
returns true while the namespace waits for recovery. The namespace is added to
an internal retry list in `NamespaceStore`.

The `startSealedAtBootRetry` goroutine in `namespace_store.go` iterates the
list at the interval of the root seal health check (one minute by default). For
each entry it calls `SetSeal` to (re-)initialize the KMS wrapper; if that
succeeds, it calls `UnsealBarrierFromStoredKeys`, which runs `GetStoredKeys` to
decrypt the stored barrier key and `UnsealWithRootKey` to open the barrier.
The standard post-unseal sequence then loads the namespace mounts and policies.
The namespace is removed from the retry list on success. Manual retry via the
unseal endpoint is also possible at any time during the retry period.

The goroutine runs on all nodes (active and performance standby) because
`postUnseal` is called on each. On standby nodes the post-unseal sequence is
limited and the goroutine has no side effects beyond the retry itself.

### Audit

Standard OpenBao request/response audit logging covers all operations.
Credentials and key material are HMAC'd by default unless `log_raw` is enabled.

## Rationale and Alternatives

`PUT /config/seal` is limited to credential rotation. Accepting a different KMS
key through this endpoint would require re-encrypting the stored barrier key,
which changes the cryptographic binding between the namespace and the KMS. That
operation is closer in risk profile to seal type migration than to a credential
update, and it warrants the explicit operator intent that `POST /migrate-seal`
enforces.

Seal type migration is kept in a separate endpoint (`POST /migrate-seal`) because
it requires key shares (Shamir) and changes the fundamental cryptographic
mechanism protecting the namespace, warranting explicit operator intent.

`WrapperConfig` from `Wrapper.SetConfig()` is preferred for the GET metadata
response over the external-key mechanism in
https://github.com/openbao/openbao/pull/3605 because it requires no changes to
`go-kms-wrapping` and reuses the output already used for the seal information table printed at server startup.
The tradeoff is that metadata completeness depends on plugin authors; a
misconfigured plugin could expose sensitive fields.

## Downsides

No significant design downsides have been identified. Operational considerations
are noted inline in the Technical Description sections above.

## Security Implications

A KMS compromise for one namespace does not compromise the barrier keys of other
namespaces or the root namespace, because each namespace's barrier key is wrapped
independently by its own KMS. This is a security improvement over a single global
key wrapping all namespace data.

Access to the namespace barrier is gated by KMS access controls. An operator who
loses KMS access loses the ability to unseal the namespace. This is the same model
as the global auto-seal and places the same responsibility on the operator to
maintain KMS availability and access.

The test-before-swap guard on `PUT /config/seal` prevents an operator from
inadvertently configuring a new wrapper that cannot read the existing stored key,
which would lock out the namespace. The guard cannot prevent a deliberate
misconfiguration, but it eliminates accidental lockout from credential mistakes.

The sudo requirement on `PUT /config/seal` and `POST /migrate-seal` ensures that
seal lifecycle operations cannot be performed by a token with only ordinary
`update` capability on the namespace path. This closes the gap noted in the
Problem Statement, where `sys/namespaces` is not currently in `PathsSpecial.Root`.

## User/Developer Experience

Operators familiar with the global auto-seal will find the namespace-level
behavior consistent. An auto-seal namespace is born unsealed and requires no
manual unseal step; there are no key shares to distribute or store.

Boot resilience is transparent: if a namespace KMS is unavailable at startup, the
server comes up normally and the namespace recovers automatically when the KMS
becomes reachable again. The `GET /v1/sys/namespaces/<path>/seal-status` endpoint
allows operators and monitoring systems to observe this state.

Namespace creation without a seal parameter continues to work exactly as before.
Existing tooling that creates namespaces via the API or CLI is unaffected.
