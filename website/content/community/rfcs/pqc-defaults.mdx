# PQC by Default

## Summary

PQC adoption is widely becoming a mandatory change. Like the removal of DSA,
DES, and 3DES, at some point default algorithms need to change.

In 2027 we should set default algorithms to ML-DSA for signing and ML-KEM for
key agreement. This should be announced now but land in v2.11.0.

## Problem Statement

Outside of the discussion of server operator _policies_ (to, for instance,
forbid usage of classical, non-PQC algorithms altogether) lies the discussion
of what the default algorithms are.

Many governments have announced aggressive transition deadlines to deprecate
classical algorithms by. Go has not adopted nor endorsed many hybrid schemes
leaving us with two options: continue defaulting to classical algorithms or
move to newer post-quantum alternatives.

We have many such user-facing default algorithms for OpenBao-generated keys:

 - PKI for CA and leaf types;
 - SSH for CA and certificate types; and
 - Identity's OIDC issuer key type.

Keys which are not generated by OpenBao are out of scope (e.g., TLS listener
certificates, issuer keys in the JWT and Kubernetes authentication mechanisms,
and more).

Some of these locations rely on libraries which have not at the time of
writing implemented

## User-facing Description

This is a breaking change.

It suggests updating several user-accessible APIs to default to PQC algorithms:

 - In PKI, to `mldsa` (with the default `key_bits` of `44`);
 - In SSH, to the equivalent of `mldsa-44`; and
 - In Identity's OIDC issuer to the equivalent of `mldsa-44`.

Other locations, as identified, will be updated here.

## Technical Description

The technical implementation of this RFC is largely trivial minus the over
indexing of tests against existing behavior.

## Rationale and Alternatives

Outside of not doing it, the only other choice is to remove default values
altogether and require However, while also breaking, this just shifts where
the default lives (now, to provisioning code), which is harder to update than
application-wide defaults.

As noted in our [API compatibility statement](/docs/api):

> :::warning
> **Backwards compatibility**: At the current version, OpenBao does not yet promise backwards compatibility even with the v1 prefix. We'll remove this warning when this policy changes. At this point in time the core API (that is, sys/ routes) change very infrequently, but various secrets engines/auth methods/etc. sometimes have minor changes to accommodate new features as they're developed.
> :::

this is within our scope to update.

## Downsides

This is a breaking change.

## Security Implications

ML-DSA is still rather new; while unfortunate that it has not had more time
to mature, given the aggressive adoption cycles of government. This thus
poses the risk that ML-DSA has some unknown weakness at the current time. If
so, we would not be the only affected application and many people would have
to patch and update applications. Weighed against the known risks of RSA and
EC algorithms (both classical and quantum), this is likely an acceptable
trade-off to make.

## User/Developer Experience

Users rely on OpenBao to be secure and to choose secure defaults. By setting
a precedence for adopting leading security guidance, we can later update the
defaults to more secure bit strengths or alternative algorithms.
